# 日報アプリ 設計案（v0.1）

社会保険労務士法人リライエがクライアント企業に提供する日報アプリの設計案です。
日報を「コミュニケーションツール」として位置づけ、入力はシンプルに保ちつつ、蓄積したデータから労務・ハラスメント問題の兆候を早めに見つけ、労務管理者が状態を管理できるようにします。

> **解釈について（要確認）**
> 音声入力の「テキオスルアケデスカラローム」は、文脈から **ハラスメント（および長時間労働・メンタル不調などの労務問題）** と解釈して設計しています。違っていたら教えてください。
> 「ローム管理者」は **労務管理者** と解釈しています。

---

## 1. 全体像

```
社員 ──日報(1分)──▶ 上長 ──コメント・スタンプ──▶ 社員
                     │
                     ▼
            夜間集計・兆候検知（自動）
                     │
                     ▼
     労務管理者（リライエ／企業の人事）── ステータス変更・対応記録
                     │
                     ▼
            社長向けダッシュボード（会社全体の状態）
```

### 利用者と権限（ロール）

| ロール | 誰が | できること |
|---|---|---|
| 社員 | クライアント企業の従業員 | 日報入力、自分の履歴閲覧、上長コメントへの返信、**労務担当にだけ届く相談** |
| 上長 | 部署の責任者 | 部下の日報閲覧、コメント（PDFの「C 上司としてアドバイス」に相当）、既読 |
| 社長（企業管理者） | クライアント企業の代表 | 会社全体の集計・ダッシュボード、ユーザー管理 |
| 労務管理者 | リライエの担当者（または企業の人事） | 担当企業の兆候アラート確認、**社員ごとのステータス変更**、対応記録 |
| システム管理者 | リライエ | 企業（テナント）の追加、労務管理者の割り当て |

1つのシステムに複数のクライアント企業を載せる **マルチテナント** 構成にします。リライエ側は担当企業を横断して見られます。

---

## 2. 日報の入力フォーマット（極力シンプル）

PDFの例（P予定 / D実績 / C上司アドバイス / A やり直せるなら / S 成長の記録 / KK 経営計画書）を土台に、スマホで1〜2分で書ける形に絞ります。

| 項目 | 必須 | 形式 | PDFとの対応 |
|---|---|---|---|
| 今日の調子 | ◯ | 5段階の顔アイコン（ワンタップ） | 新規（兆候検知の要） |
| 今日やったこと | ◯ | 自由記述（音声入力可） | D 実績 |
| 今日もう一度やり直せるなら | | 自由記述 | A |
| 気づき・成長の記録 | | 自由記述 | S |
| 明日の予定 | | 自由記述 | P 予定 |
| 困っていること・相談したいこと | | 自由記述＋「**上長には見せず労務担当にだけ伝える**」チェック | 新規 |
| 退勤時刻 | | 時刻（任意・企業設定でON/OFF） | タイムスケジュール欄の簡略版 |
| 経営計画書の気になる一文 | | 自由記述（企業設定でON/OFF） | KK |

- 時間割（8:30〜17:30の予定/実績表）は入力負担が大きいので、初期版では「やったこと」の自由記述にまとめます。必要なら企業ごとにONにできる拡張項目にします。
- タイピングテストの点数も同様に「企業ごとの任意項目」で対応できるようにします。
- 「相談したいこと」を上長を通さず労務担当へ届けられるのは、ハラスメントの加害者が上長であるケースに備えるためです（パワハラ防止法の相談窓口の考え方に沿う）。

---

## 3. 上長とのやりとり

- 日報ごとにコメントのスレッド（上長 ⇄ 社員で何往復でも可）
- ワンタップの反応（👍「見たよ」など）と既読表示
- 上長が一定日数コメントも既読もしていない場合は、それ自体を兆候として扱う（コミュニケーション不足のサイン）

---

## 4. 問題兆候の検知（夜間に自動集計）

毎晩、Cloudflare の定期実行（Cron）で社員ごとの指標を集計し、ルールに当てはまるとアラートを作ります。

| 兆候 | ルール例（初期値・企業ごとに調整可） |
|---|---|
| 調子の低下 | 直近7日平均が前4週平均より1.0以上低い／「2以下」が3日連続 |
| 未提出 | 3営業日連続で未提出、または提出率が急に下がった |
| 長時間労働 | 退勤時刻から推定した時間外が月45時間ペースを超えそう |
| 気になる言葉 | 「怒鳴られ」「無視され」「辞めたい」「眠れない」「死にたい」等の辞書に一致（辞書は労務管理者が編集可） |
| 記述量の急減 | 文字数が普段の3割未満の日が続く |
| 労務担当への相談 | 「労務担当にだけ伝える」が使われたら即アラート |
| 上長の無反応 | 部下の日報に7日間コメント・既読なし |

- アラートには「低・中・高」の重要度をつけ、「死にたい」等の緊急語は即時に高として通知します。
- 第2段階として、AI（Workers AI または Claude API）で文章のトーンを判定する機能を検討します。要配慮個人情報（健康状態など）を外部に送るかどうかの判断が必要なので、初期版はルール判定のみにします。

---

## 5. 労務管理者によるステータス管理

社員ごとに「今の状態」を労務管理者が設定・変更できます。自動判定はあくまで材料で、最終判断は人が行います。

**社員のステータス**: 良好 / 様子見 / 要フォロー / 対応中 / 休職中

**アラート（案件）の流れ**: 新規 → 確認中 → 面談調整中 → 対応中 → 解決（クローズ）

- 変更時は理由メモを残し、誰がいつ変えたかを履歴（監査ログ）として保存
- 社員ごとのページで「調子の推移グラフ」「アラート履歴」「対応記録」「日報」を1画面で確認
- 社長向けには個人の相談内容は見せず、会社全体の傾向（提出率、平均コンディション、要フォロー人数）を表示

## 6. 技術構成（Cloudflare）

| 役割 | 採用技術 |
|---|---|
| ソース管理 | GitHub（非公開リポジトリ推奨）。main へのマージで自動デプロイ（GitHub Actions） |
| アプリ本体 | Cloudflare Workers（Hono フレームワーク）＋ 静的アセット配信 |
| 画面 | スマホ優先のシンプルなWeb画面（ホーム画面に追加できるPWA） |
| データベース | Cloudflare D1（SQLite） |
| 定期集計 | Workers の Cron Triggers（毎晩） |
| 認証 | メールアドレス＋パスワード（招待制）。パスワードは PBKDF2 でハッシュ化、セッションは HttpOnly Cookie。社員の自己登録はさせず、企業管理者／リライエが招待リンクを発行 |
| 通知 | 第2段階で Chatwork API（リライエの日常の連絡手段）とメール |

### 主なテーブル（D1）

- `tenants`（クライアント企業）
- `users`（ロール、所属企業、上長ID）
- `reports`（日報本体、日付、調子、各記述欄）
- `comments`（日報へのコメント・反応・既読）
- `consultations`（労務担当にだけ届く相談）
- `daily_metrics`（夜間集計結果）
- `alerts`（兆候アラート、重要度、案件ステータス）
- `employee_status`（社員ごとの現在ステータス）
- `status_history` / `audit_logs`（変更履歴）
- `keyword_rules`（検知用キーワード辞書）

---

## 7. 個人情報・コンプライアンス上の配慮

- 健康・メンタルに関する記述は要配慮個人情報に当たり得るため、閲覧できる人をロールで厳密に制限し、閲覧ログを残します
- 労務担当への相談は上長・社長には表示しません
- データの保存期間（例：退職後3年）を企業ごとに設定可能にします
- 利用開始時に社員へ利用目的（健康確保・職場環境改善のため）を明示する同意画面を設けます

---

## 8. 進め方（段階的リリース）

1. **第1段階（MVP）**: 認証・招待、日報入力、履歴、上長コメント、労務担当への相談、労務管理者のステータス変更
2. **第2段階**: 夜間集計と兆候アラート、ダッシュボード、Chatwork／メール通知
3. **第3段階**: AIによる文章トーン判定、企業ごとの任意項目（時間割、タイピングテスト等）、CSV出力
